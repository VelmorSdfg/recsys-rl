# Что происходит, когда рекомендательную модель дообучают с подкреплением?

Я обучил GPT-2 предсказывать следующий трек пользователя, а потом дообучил её с подкреплением
(GRPO), чтобы рекомендации получали больше награды: выше доля дослушивания, больше лайков, длиннее
сессия. Награду считает отдельная модель (reward model), обученная на реальных откликах. Меня
интересовало, можно ли поднять награду и не потерять релевантность. И в какой момент модель
перестаёт угождать пользователю и начинает обманывать reward model.

**Коротко: награду можно поднять совсем немного.** Без потери точности предсказанное дослушивание
растёт на 1-1,5 %. Дальше RL рекомендации уже не улучшает, а эксплуатирует слабости reward model,
в первую очередь через длину трека. При слабом KL-штрафе модель вырождается в набор одних и тех же
коротких треков для всех. Результат отрицательный, и в отчёте видно, откуда он берётся.

Данные: [Yambda-50M](https://huggingface.co/datasets/yandex/yambda) от Яндекс Музыки, 46,5 млн
прослушиваний 9 238 пользователей за 300 дней, с долей дослушивания, длиной трека и лайками.
Разбиение по времени: test - последние 7 дней, valid - 7 дней перед ними, обучение - всё, что раньше.

Подробности лежат в [REPORT.md](REPORT.md): качество reward models, все 23 RL-прогона, разбор
поведения, генерация на несколько шагов и долгосрочные цели.

пользователей, интервалы посчитаны парным бутстрапом по пользователям.

## Главное

1. Немного награды достаётся бесплатно. При сильном штрафе предсказанное дослушивание растёт на
   1-1,5 %, и NDCG@10 не падает, а при β = 5 даже значимо растёт. Дальше цена резко растёт: +2,7 %
   награды стоят 2 % точности, а +6 % стоят уже 15 %.
2. После этого RL обманывает reward model, и на реальных данных это видно. Когда оптимизируются
   лайки, reward model обещает их на 70 % больше. Но среди рекомендаций, которые пользователи
   действительно послушали, доля лайков не изменилась. Реальное дослушивание при этом растёт, до
   +17 %, но почти весь рост даёт переход на короткие треки: короткий трек проще дослушать.

   ![предсказание против реальности](results/analysis/reward_vs_real.png)
3. У каждой награды свой хак, и почти всегда он связан с длиной трека. Дослушивание тянет к
   коротким трекам, лайки и время прослушивания тянут к длинным (480-520 с). Продолжение сессии
   приводит к трекам по 54 секунды: если трек длится минуту, следующее прослушивание в пределах 30
   минут случается само собой. Каталог при этом сужается. При сильной оптимизации 82-100 % выдачи
   занимают одни и те же 100 треков, у всех пользователей.
4. Оптимальный компромисс можно посчитать заранее, и GRPO его иногда не достигает. У одношаговой
   задачи `награда - β * KL` есть точное решение `π*(a) ~ π_ref(a) * exp(r(a) / β)`. Его получаем
   без обучения, простым переранжированием (линии на графике). При β >= 0.5 GRPO ложится ровно на
   эту кривую. При малом β мешает стандартная нормировка GRPO на разброс внутри группы. Когда
   политика сужается, разброс падает, преимущества раздуваются, и KL-штраф перестаёт её удерживать.
   Модель схлопывается в точку, которая хуже оптимума сразу по обеим осям. Если нормировать на
   фиксированный масштаб, как в Dr. GRPO, этого не происходит.
5. При генерации на 5 шагов ошибка накапливается. Я дописывал рекомендации модели в историю, как
   будто пользователь их послушал. К пятому шагу NDCG@10 падает вдвое (0.107 -> 0.048), и модель
   залипает на одном треке. Для RL-модели рабочая reward model с каждым шагом ставит всё более
   высокие оценки, а проверочная всё более низкие. Значит, награда по таким rollout'ам
   систематически завышена.
6. Долгосрочные цели в офлайн-данных почти не видны. Если сравнивать сессии одного пользователя,
   их качество почти не связано с тем, вернётся ли он на следующий день: корреляция 0.026.
   Разница есть только у самых плохих сессий, после них возвращаются на 2,4 п. п. реже. Удержание
   надо проверять онлайн, а награду давать за сессию целиком, а не за отдельный трек.

## Как это сделано

Протокол. Все модели обучаются на событиях до начала valid, гиперпараметры выбираются по valid,
test - последние 7 дней. Словарь состоит из 50 тыс. самых популярных треков, это 80 %
прослушиваний. В каждой тестовой точке модель видит 200 предыдущих прослушиваний и угадывает
следующий трек. Если трека нет в словаре (так у 27 % точек), это считается промахом.

Базовая модель. GPT-2 из `transformers` на 4 слоя и 16 млн параметров, токены - id треков,
кросс-энтропия по всем 50 тыс. трекам. NDCG@10 у неё 0.110, вдвое выше, чем у эвристики "самое
частое в истории" (0.053).

Reward model. Это трансформер по истории, где каждое событие - трек вместе с тем, насколько его
дослушали. Для трека-кандидата он предсказывает долю дослушивания, лайк и продолжение сессии.
Дослушивание получается хорошо: AUC 0.881 против 0.751 у лучшей эвристики. Но для RL важнее
другое: умеет ли модель выбирать между треками для одного и того же пользователя. По этой метрике
дослушивание даёт 0.743, лайк 0.689, а продолжение сессии 0.556, что почти не лучше монетки.
Оптимизировать продолжение сессии значит оптимизировать шум.

RL. В GRPO политика по истории пользователя выбирает 16 треков, reward model оценивает каждый, и
политика сдвигается к тем, что оказались лучше среднего. Действие здесь - один трек, поэтому штраф
за отход от исходной модели считается точно, по всему словарю. Я перебрал силу штрафа, две
нормировки, семь функций награды и горизонт в 1 и 5 шагов.

Чтобы понять, настоящий ли рост награды, я проверял его тремя способами:
* Вторая reward model другой архитектуры. Если RL поднимает оценку первой модели, а второй нет,
  значит, он эксплуатирует ошибки первой. Правда, модели похожи (корреляция 0.98), поэтому так
  ловится только грубый обман.
* Реальные отклики. Берутся рекомендованные треки, которые пользователь действительно послушал в
  ближайших 10 прослушиваниях, и для них смотрятся реальное дослушивание и лайки.
* Аналитический оптимум, с которым сравнивается каждый RL-прогон.

## Ответы на вопросы задания

* Как меняется поведение после RL? Награда растёт, но модель получает её за счёт длины трека, отказа
  от знакомых треков и сужения каталога. Подробнее в [отчёте](REPORT.md#поведение-модели-после-rl).
* Сохраняется ли релевантность? При сильном штрафе да. Если штраф ослабить, она падает вместе с
  покрытием каталога: [релевантность](REPORT.md#релевантность-и-разнообразие).
* Можно ли приблизиться к долгосрочным целям? Офлайн-сигналы удержания слабые, и их легко взломать.
  В отчёте разобрано, какие сигналы есть в данных, как строить награду за сессию и что можно
  проверить только A/B-тестом: [долгосрочные цели](REPORT.md#долгосрочные-цели).
* Что происходит при генерации нескольких шагов? Модель уходит от реальной истории, точность падает
  вдвое, ошибка reward model накапливается: [несколько шагов](REPORT.md#генерация-на-несколько-шагов).
* Каков компромисс? Его показывает кривая выше, разбор в
  [отчёте](REPORT.md#компромисс-между-релевантностью-и-наградой). Как влияет выбор функции награды,
  видно в [таблице всех наград](REPORT.md#разные-функции-награды).

## Ограничения и что дальше

* Рост награды измерен reward models, а не людьми. Проверка на реальных откликах смещена: в неё
  попадают только треки, которые пользователь и так собирался слушать.
* Вторая reward model слишком похожа на первую. Лучше подошёл бы судья, обученный на других
  пользователях или других признаках.
* Почти все хаки идут через длину трека. Следующий шаг - награда с поправкой на длину или явное
  ограничение на распределение длин.
* Датасет один, тест длится неделю. Треки вне словаря (27 % целей) модель рекомендовать не может.
* Что ещё стоит попробовать: DPO на реальных парах "дослушал / пропустил" вместо reward model,
  критик для награды за сессию вместо rollout'ов, ограничения на разнообразие прямо в RL-цели.

## Запуск

```bash
pip install -r requirements.txt
# multi_event.parquet из huggingface.co/datasets/yandex/yambda (flat/50m) положить в папку
# и указать её в YAMBDA_RAW (по умолчанию ../recsys_autofeatures/data/raw_yambda)
python src/prepare.py                         # прослушивания, метки, разбиение (~3 мин)
python src/train_gpt.py                       # базовая GPT-2 (~2 ч на RTX 4060)
python src/train_reward.py --name A           # reward model A (~50 мин)
python src/train_reward.py --name B --d 192 --layers 3 --seed 1    # проверочная модель B
python src/rm_report.py                       # качество reward models внутри пользователя
python src/rl_grpo.py --reward ratio --beta 1 # RL, ~15 мин на прогон; --adv fixed, --horizon 5
python src/analysis.py                        # аналитический оптимум, таблицы, графики
python src/multistep.py --models base rl/ratio_b1   # генерация на 5 шагов
python src/longterm.py                        # связь сигналов сессии с возвращением
```

Видеопамять на процесс ограничена переменной `RECSYS_GPU_GB` (по умолчанию 5 ГБ), на пиках уходит
2-3,4 ГБ. Что лежит в каждом файле, описано в [отчёте](REPORT.md#структура-кода).
