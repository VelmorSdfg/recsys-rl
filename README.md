# Что происходит, когда рекомендательную модель дообучают с подкреплением?

GPT-2 учится предсказывать следующий трек пользователя. Затем её дообучают с подкреплением (GRPO),
чтобы рекомендации получали больше награды: выше доля дослушивания, больше лайков, дольше сессия.
Награду считает отдельная модель (reward model), обученная на реальных откликах. Вопрос: удаётся ли
поднять награду, не потеряв релевантность, и где модель начинает обманывать reward model вместо
того, чтобы радовать пользователя.

**Коротко: награду можно поднять лишь немного.** Без потери точности предсказанное дослушивание
растёт на 1–1,5 %. Дальше RL уже не улучшает рекомендации, а пользуется слабостями reward model,
прежде всего через длину трека. При слабом KL-штрафе модель вырождается в «одни и те же короткие
треки для всех». Результат отрицательный, но каждая его часть объяснена и проверена на реальных
откликах.

Данные — [Yambda-50M](https://huggingface.co/datasets/yandex/yambda) (Яндекс Музыка): 46,5 млн
прослушиваний 9 238 пользователей за 300 дней, с долей дослушивания, длиной трека и лайками.
Разбиение по времени: test — последние 7 дней, valid — 7 дней до них, всё обучение — раньше.

**Все детали — в [REPORT.md](REPORT.md):** качество reward models, все 23 RL-прогона, разбор
поведения, генерация на несколько шагов, долгосрочные цели.

## Главное

1. **Немного награды достаётся бесплатно.** При сильном штрафе предсказанное дослушивание растёт на
   1–1,5 %, а NDCG@10 не падает, при β = 5 даже значимо растёт. Дальше компромисс крутой: +2,7 %
   награды стоят 2 % точности, +6 % — 15 %.
2. **Дальше RL обманывает reward model, и это видно на реальных данных.** При оптимизации лайков
   reward model обещает +70 % лайков. А среди рекомендаций, которые пользователи реально послушали,
   доля лайков не выросла. Дослушивание реально растёт (до +17 %), но в основном потому, что модель
   переходит на короткие треки, а короткий трек проще дослушать.

   ![предсказание против реальности](results/analysis/reward_vs_real.png)
3. **У каждой награды свой «хак», и почти всегда через длину трека.** Дослушивание тянет к коротким
   трекам, лайк и время прослушивания — к длинным (480–520 с). Продолжение сессии — к
   54-секундным: после минутного трека «следующее прослушивание в течение 30 минут» случается само
   собой. Одновременно сужается каталог: при сильной оптимизации 82–100 % выдачи — одни и те же
   100 треков для всех.
4. **Оптимальный компромисс известен заранее, а GRPO его иногда ломает.** Для одного шага у задачи
   «награда − β·KL» есть точное решение π* ∝ π_ref·exp(r/β), и его можно посчитать без обучения,
   переранжированием (линии на графике). GRPO при β ≥ 0.5 попадает ровно на эту кривую. При малом β
   стандартная нормировка GRPO на разброс внутри группы раздувает преимущества по мере сужения
   политики, KL-штраф перестаёт держать, и модель коллапсирует в точку хуже оптимума по обеим осям.
   Нормировка на фиксированный масштаб (как в Dr. GRPO) от этого защищает.
5. **Генерация на 5 шагов вперёд накапливает ошибку.** Если дописывать свои рекомендации в историю,
   как будто пользователь их послушал, NDCG@10 к пятому шагу падает вдвое (0.107 → 0.048), и модель
   залипает на одном треке. У RL-модели рабочая reward model с каждым шагом ставит всё больше, а
   проверочная — всё меньше: награда по таким rollout'ам систематически завышена.
6. **Долгосрочные цели офлайн почти не видны.** Если сравнивать сессии одного пользователя, их
   качество почти не связано с тем, вернётся ли он на следующий день (корреляция 0.026). Заметно
   только то, что после самых плохих сессий возвращаются на 2,4 п. п. реже. Удержание нужно
   проверять онлайн, а награждать — за сессию, а не за отдельный трек.

## Как это сделано

**Протокол.** Всё обучение — на событиях до начала valid, решения — по valid, test — последние 7
дней. Словарь — 50 тыс. популярных треков (80 % прослушиваний). На каждую тестовую точку модель
видит 200 предыдущих прослушиваний и должна угадать следующий трек. Если трек вне словаря (27 %
точек), это честно считается промахом.

**Шаг 1. Базовая модель.** GPT-2 из `transformers`: 4 слоя, 16 млн параметров, токены — id треков,
кросс-энтропия по всем 50 тыс. трекам. NDCG@10 = 0.110, вдвое лучше эвристики «самое частое в
истории» (0.053).

**Шаг 2. Reward model.** Трансформер по истории, где каждое событие — трек плюс то, насколько его
дослушали. Для трека-кандидата он предсказывает долю дослушивания, лайк и продолжение сессии.
Дослушивание он предсказывает хорошо: AUC 0.881 против 0.751 у лучшей эвристики. Важнее для RL
другое: насколько хорошо модель выбирает между треками для одного и того же пользователя. Там
дослушивание — 0.743, лайк — 0.689, а продолжение сессии — 0.556, почти монетка. Оптимизировать
последнее значит оптимизировать шум.

**Шаг 3. RL.** GRPO: на историю пользователя политика выбирает 16 треков, reward model оценивает
каждый, политика сдвигается к тем, что лучше среднего. Штраф за отход от исходной модели считается
точно, по всему словарю: действие — один трек. Перебраны сила штрафа, две нормировки, семь функций
награды и горизонт в 1 и 5 шагов.

**Как проверялось, что награда настоящая.** Три независимых способа:
* **вторая reward model** другой архитектуры. Если RL поднимает оценку первой, но не второй, это
  эксплуатация её ошибок. Но модели похожи (корреляция 0.98), поэтому ловится только грубый обман;
* **реальные отклики:** для рекомендованных треков, которые пользователь действительно послушал в
  ближайших 10 прослушиваниях, — его реальное дослушивание и лайки;
* **аналитический оптимум** — эталон, с которым сравнивается каждый RL-прогон.

## Ответы на вопросы задания

* **Как меняется поведение после RL?** Награда растёт, но модель добывает её через длину трека,
  отказ от уже знакомого и сужение каталога. Подробно — в [отчёте](REPORT.md#поведение-модели-после-rl).
* **Сохраняется ли релевантность?** При сильном штрафе — да, при ослаблении штрафа падает вместе с
  покрытием каталога. Подробно — в [отчёте](REPORT.md#релевантность-и-разнообразие).
* **Можно ли приблизиться к долгосрочным целям?** Офлайн-сигналы удержания слабые и легко
  взламываются. В отчёте разобрано, какие сигналы есть в данных, как строить сессионную награду и
  что требует A/B-теста: [долгосрочные цели](REPORT.md#долгосрочные-цели).
* **Что при генерации нескольких шагов?** Модель уходит от реальной истории, точность падает вдвое,
  ошибка reward model накапливается: [несколько шагов](REPORT.md#генерация-на-несколько-шагов).
* **Каков компромисс?** Кривая выше и [разбор](REPORT.md#компромисс-между-релевантностью-и-наградой).
  Влияние функции награды — в [таблице всех наград](REPORT.md#разные-функции-награды).

## Ограничения и что дальше

* Рост награды измерен reward models, а не людьми. Проверка на реальных откликах смещена: в неё
  попадают только треки, которые пользователь и так собирался слушать.
* Вторая reward model слишком похожа на первую. Лучше был бы судья на других пользователях или
  признаках.
* Почти все хаки идут через длину трека. Следующий шаг — награда с поправкой на длину или явное
  ограничение на распределение длин.
* Один датасет, неделя теста. Треки вне словаря (27 % целей) модель рекомендовать не может.
* Дальше: DPO на реальных парах «дослушал / пропустил» как альтернатива reward model, критик для
  сессионной награды вместо rollout'ов, ограничения на разнообразие прямо в RL-цели.

## Запуск

```bash
pip install -r requirements.txt
# multi_event.parquet из huggingface.co/datasets/yandex/yambda (flat/50m) положить в папку
# и указать её в YAMBDA_RAW (по умолчанию ../recsys_autofeatures/data/raw_yambda)
python src/prepare.py                         # прослушивания, метки, разбиение (~3 мин)
python src/train_gpt.py                       # базовая GPT-2 (~2 ч на RTX 4060)
python src/train_reward.py --name A           # reward model A (~50 мин)
python src/train_reward.py --name B --d 192 --layers 3 --seed 1    # проверочная модель B
python src/rm_report.py                       # качество reward models внутри пользователя
python src/rl_grpo.py --reward ratio --beta 1 # RL, ~15 мин на прогон; --adv fixed, --horizon 5
python src/analysis.py                        # аналитический оптимум, таблицы, графики
python src/multistep.py --models base rl/ratio_b1   # генерация на 5 шагов
python src/longterm.py                        # связь сигналов сессии с возвращением
```

Видеопамять на процесс ограничена переменной `RECSYS_GPU_GB` (по умолчанию 5 ГБ), пики — 2–3,4 ГБ.
Описание всех файлов — в [отчёте](REPORT.md#структура-кода).
